# 배포 안정화 — 새 버전을 내고 prod 를 올려도 안 깨지게

작성 2026-08-02 · 짝 문서: `WEBVIEW_BRIDGE_CONTRACT.md`(구버전 앱 ↔ 최신 웹 축)

이 문서는 **배포 축**을 다룬다. 앱 버전 축은 짝 문서에 있다.

## 배포가 사용자를 깨뜨리던 세 지점 (전부 실측)

### 1. 안내값이 손으로 관리돼 이미 틀어져 있었다

`version.py` 의 `app_ios_version` / `app_android_version` 은 사람이 적는 값이었다. 2026-08-01 측정 시
**스토어는 1.0.5 인데 안내값은 1.0.1** 이었다 → 1.0.2~1.0.4 사용자는 업데이트 안내를 한 번도 못 받았다.
구버전 앱이 계속 남고, 그 앱에 없는 네이티브 기능을 최신 웹이 부르면서 "버그처럼 보이는 무반응"이 난다.

반대 방향 사고도 있다: 심사 통과 전에 미리 올리면 **없는 버전으로 안내** → 스토어에 가도 없음 →
앱을 다시 열면 또 안내 = 무한 업데이트 모달.

### 2. 배포하면 열려 있던 탭이 깨지는데, 되살릴 장치가 수기였다

prod 배포는 컨테이너를 통째로 교체하므로 이전 빌드의 해시 자산이 서버에서 사라진다. 사용자의 웹뷰는
그대로 열려 있으므로, 그 뒤에 폰트·wasm·사운드처럼 **나중에 요청되는 자산**을 부르면 404 다.
복구 수단은 `web_version` 을 손으로 올려야 걸리는 새로고침뿐이었고, 잊으면 그대로 방치됐다.

### 3. 사라진 자산이 404 가 아니라 **index.html 을 200 으로** 돌려줬다

nginx 의 강캐시 규칙이 확장자 목록(`js|css|png|...|woff2?`) 기준이라 `.wasm` `.otf` `.mp3` 가 빠져 있었다.
빠진 것들은 SPA 폴백(`try_files $uri $uri/ /index.html`)으로 흘러가 **HTML 을 200 으로** 받았다.
sql.js 는 wasm 대신 HTML 을 받고 폰트는 디코드에 실패한다 — "파일이 없다" 가 아니라 원인 모를 에러가 된다.

> 배포 전 prod 에서 실증: `GET /assets/does-not-exist.wasm` → **200**(HTML). 지금은 404 여야 정상이다.

## 무엇을 바꿨나

| 문제 | 조치 | 파일 |
|---|---|---|
| 안내값 수기 관리 | 스토어 실조회(iTunes lookup + Play 상세 페이지), 1시간 캐시 | `heyvoca_back/app/services/store_version.py` |
| 배포 후 낡은 탭 | 빌드마다 `/version.json` 지문 생성 → 프론트가 폴링해 **안전한 순간에** 새로고침 | `vite.config.js`, `src/utils/buildVersion.js` |
| 사라진 자산이 HTML 200 | `/assets/` 는 immutable+404, 그 외 정적 확장자도 404 로 정직하게 | `heyvoca_front/nginx.conf` |
| 배포 후 확인 수단 없음 | 위 셋을 실호출로 검사 | `scripts/verify-deploy.sh` |

### 안내값 자동화 규칙

- **값이 내려가지 않는다.** 조회 실패 → 마지막 성공값(7일 보관) → env(`APP_LATEST_*`) → 상수 폴백 순.
  어느 단계든 폴백보다 낮은 값은 채택하지 않는다. "모르면 그대로 둔다" 가 항상 안전한 쪽이다.
- **캐시버스터 필수.** iTunes lookup 은 같은 URL 을 반복하면 CDN 이 낡은 값을 무기한 고정한다(반복 재현).
- **Play 는 공식 공개 API 가 없다.** 상세 페이지 파싱이라 깨지면 조용히 폴백한다. 정확한 값이 필요하면
  서비스계정 API(`scripts/store/play.mjs status`)를 쓴다.
- 응답의 `app_version_source` 는 **진단 전용**이다. 클라이언트가 이걸로 기능을 분기하면 안 된다.

### 새로고침 규율

- **작업 중에 새로고침하지 않는다.** 새 빌드를 감지해도 표시만 하고, 화면이 가려졌다가 다시 돌아오는
  순간(앱 재진입)에 적용한다. 학습 도중의 갑작스러운 새로고침은 우리가 없애려는 버그보다 나쁘다.
- **모르면 아무것도 하지 않는다.** `version.json` 을 못 읽으면 조용히 넘어간다. 잘못된 판정으로 만드는
  무한 새로고침이 최악이다.
- 지문은 번들 콘텐츠 해시라 **내용이 바뀔 때만** 바뀐다 → 같은 코드를 재배포해도 새로고침이 안 걸린다.

### nginx 캐시는 **경로**로 나눈다

확장자로 나누면 안 된다. `public/` 에서 그대로 복사되는 파일(`dummy_vocalist/*.json`, `vite.svg`)은
파일명에 해시가 없어서, 확장자 기준으로 `immutable` 을 걸면 내용을 바꿔 배포해도 브라우저가 1년 동안
옛 파일을 쓴다. 해시가 보장되는 건 `/assets/` 뿐이다.

## 배포할 때

```bash
bash heyvoca_service/scripts/release-status.sh     # 무엇을 해야 하는지(읽기 전용)
cd heyvoca_service && ./deploy.sh prod             # 권한 분류기에 막히면 사용자가 ! 로 실행
bash heyvoca_service/scripts/verify-deploy.sh prod # 이게 통과해야 배포 완료
```

`verify-deploy.sh` 가 검사하는 것: back/front 기동 · **빌드 지문 존재와 no-store** ·
**없는 자산이 404 인가** · 안내값과 출처 · 안내값이 게시본보다 높지 않은가(무한 모달 방지) ·
`min_app_version` 이 안내값보다 높지 않은가(강제 업데이트가 막다른 길이 되는 조합).

## 아직 안 한 것

- **백엔드가 클라이언트 버전을 모른다.** 요청 헤더에도 DB 에도 없다 → "구버전 앱 사용자 비율"을 알 수
  없고, 폴백을 언제 지워도 되는지·`min_app_version` 을 언제 올려도 되는지 판단할 근거가 없다.
  다음 단계는 `X-Client` 헤더를 받아 **기록만** 하는 것(분기 금지).
- 앱이 직접 호출하는 API 2개(`/study/log`, `/mainpage/user_study_history`)는 앱 릴리스와 수명이
  묶인다 → **응답 필드 삭제·이름변경 금지, 추가만.** 코드로 강제되지 않으니 리뷰에서 봐야 한다.
- DB 마이그레이션과 구코드의 공존(컨테이너 교체 순간)은 이번 범위 밖이다.
